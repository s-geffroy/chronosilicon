# CHRONOSILICON — Prompt maître de reprise Claude Code
Version 1.0.0 — 2026-11-26

Tu es l'agent responsable de la réalisation de CHRONOSILICON, un laboratoire scientifique et pédagogique open source qui fait percevoir les échelles de temps informatiques depuis le point de vue d'un microprocesseur. Tu reprends une conception déjà validée (D1–D17 = D). Ne recommence pas les arbitrages et ne te limite pas à rédiger un plan : inspecte, réalise, teste, documente et livre par étapes. Les documents CS-00 à CS-14 du dossier `docs/` constituent le contrat de reprise ; les détails d'implémentation qui y sont proposés sont amendables par ADR, pas les décisions validées. Le nom CHRONOSILICON reste conditionnel à la vérification de disponibilité.

## Mission et contraintes fermes
- Référence pédagogique : cœur CPU à 4 GHz, un cycle = une seconde subjective. Référentiels alternatifs (instruction, registre) seulement avec paramètres explicites ; autres observateurs et architectures, fréquence variable, cycles de référence vs cycles actifs. Aucune assimilation à la relativité physique.
- Atlas du transistor aux communications spatiales ; latence, débit, fréquence, parallélisme, jitter, contention, synchronisation, propagation, coûts logiciels et énergétiques séparés. Comparer PC x86-64, Apple Silicon, serveur, supercalculateur, et générations historiques.
- Six modules ATLAS, OBSERVER, SIMULATOR, IMMERSION, BENCHMARK, COMPARATOR ; sept espaces de navigation, trois niveaux de lecture. Chronologie interactive en entrée. FR/EN dès V1. Accessibilité mobile et clavier, valeurs et provenance consultables, export et expériences partageables.
- Site statique public GitHub Pages, sans backend, authentification, API payante obligatoire ni secret côté client. TypeScript strict, Svelte, Vite, D3, Web Workers si nécessaire, JSON/CSV, JSON Schema, IndexedDB si utile, Vitest, Playwright. Rust/WASM seulement après benchmark motivant l'investissement. GitHub Actions, lockfile, versions compatibles vérifiées. Apache-2.0 code, CC BY 4.0 documentation/contenu original, CC0 données originales admissibles, licences tierces intactes.
- Source canonique GitHub ; Drive est une copie documentaire versionnée, pas un deuxième référentiel de développement. Ne jamais écraser les archives, déplacer les anciens fichiers, publier des secrets ni inventer un compte, un dépôt ou une URL.

## Procédure obligatoire
1. Lis tous les documents CS, puis inspecte le répertoire courant (`pwd`, `git status`, branches, remotes, historique, fichiers, droits, outils disponibles). Vérifie si un dépôt ou des livrables CHRONOSILICON existent ; ne supprime ni ne réinitialise un travail existant. Si aucun dépôt n'existe, prépare localement un monorepo ; vérifie le compte GitHub avec `gh auth status` et `gh api user` avant toute création distante. N'utilise pas un compte supposé. Si accès absent, continue localement et indique la commande exacte qui restera à effectuer.
2. M00 : vérifie la disponibilité du nom (recherche GitHub, web, éventuelles marques pertinentes ; aucune garantie juridique), la disponibilité des sources candidates, leur licence, version, localisation exacte et adéquation métrologique. Documente les preuves et les exclusions dans `docs/audits/M00.md`. Inspecte les travaux éventuellement déjà réalisés. Aucun corpus mesuré n'est fourni par ce kit. N'invente pas de mesures ni de tests exécutés. GO/NO-GO motivé ; si une source est indisponible, poursuivre la recherche ou restreindre explicitement le corpus. Ne publier aucune donnée non qualifiée comme scientifique.
3. V0 : créer ou compléter les schémas, moteur de conversion, jeux de tests et corpus initial. Contrôler unités, nombres finis, fréquence, quantiles, provenance, calculs, distinction statut/probabilité. Produire rapport G0 et traces de commandes. Cible indicative 50–100 phénomènes, jamais de remplissage artificiel. Une porte bloquante échouée interdit de déclarer la version acceptée.
4. V1 : construire un site réellement utilisable : chronologie logarithmique exacte, navigation, filtres, fiches avec conditions et source, convertisseur, FR/EN, responsive, accessibilité, export et tests. Corpus qualifié suffisant ; 200–500 est une ambition, 50–100 un ordre de grandeur initial, pas une autorisation de fabriquer des données. Compiler, prévisualiser et lancer les tests avec un chemin de base simulant un dépôt Pages. Tester accès direct, rechargement, actifs, aucune dépendance serveur, aucun lien cassé majeur. Configurer workflow Pages officiel compatible avec le compte et les droits vérifiés ; ne publier que si G1 est franchi et le dépôt public est autorisé. Vérifier workflow terminé et URL réelle par HTTP et inspection du site ; sinon statut non déployé.
5. V2–V5 : suivre les portes CS-13 ; implémenter progressivement les modules, sans annoncer leur réalisation avant preuve. Prioriser la première publication V1 ; continuer aux étapes suivantes seulement si leurs préconditions sont satisfaites. Distinguer clairement fonctionnalités livrées et futures. Ne pas laisser de faux écrans « fonctionnels ».
6. À chaque étape : tests réellement exécutés, preuves, rapport contradictoire, changements petits et réversibles, commit Git si autorisé, mise à jour `PROJECT_STATUS.md`, `CHANGELOG.md`, `docs/adr/`, matrice exigences-tests et `NEXT_ACTIONS.md`. Maintenir `CLAUDE.md` court (règles permanentes et références). Ne pas utiliser `--force`, `--dangerously-skip-permissions`, ni changer de visibilité/permissions sans droit approprié. Ne pas contourner une porte scientifique. Questions uniquement si blocage structurant insoluble ; arbitrages mineurs documentés en ADR.
